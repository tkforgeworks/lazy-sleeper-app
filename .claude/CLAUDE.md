# lazy-sleeper-app — Claude reference

Client app for Lazy Sleeper (Sleeper NFL fantasy draft/in-season helper). **Presentation only** — all domain
logic lives in the Python/FastAPI backend repo `tkforgeworks/lazy-sleeper`; this app consumes its API and
never reimplements logic. Keep this file in sync as decisions land.

## Repo state

- No app code yet. Repo contains only this baseline (README, .gitignore, Claude reference, settings hook).
- Backend is still in development (as of 2026-08-19: M0/M1 done, M2 benchmark scoreboard in progress) and is
  not ready to build against. Do not start the app skeleton until the backend's `/board` endpoint exists
  (backend milestone M3). First client story: **LS-39** (Flutter read-only board/companion view).
- `main` is protected by the org standard ruleset (`tkforgeworks/.github/docs/branch-protection-ruleset.md`):
  PR-only, no force-push/delete, no bypass. **No `required_status_checks` rule yet** — CI does not exist.
  When CI is added, PATCH the ruleset to add the check (see the org doc's "Updating an existing ruleset"),
  and only after the check has reported on a PR at least once.
- Org shared standards (reusable CI workflows, release notes) live in `tkforgeworks/.github` — adopt from
  there rather than hand-rolling. Note the existing reusable CI workflows are TypeScript/Electron-oriented;
  a Flutter CI workflow will need to be authored (ideally as a new reusable `ci-flutter.yml` in
  `tkforgeworks/.github` so the upcoming org Flutter project can share it).

## Decisions inherited from the backend (see `lazy-sleeper/docs/execution-plan-analysis_20260816.md` §7)

- **Stack: Flutter** — desktop + web + mobile from one codebase (OQ-3). First Flutter project in the org.
- **Two repos** (OQ-13): `lazy-sleeper` = backend (API, engines, ingestion, HTML fallback page);
  `lazy-sleeper-app` = Flutter client, never touches logic. Separate CI per repo.
- **API-first**: FastAPI endpoints (`/board`, `/draft/{id}/state`, `/players/{id}`, `/waivers/week/{n}`, ...)
  are the contract. OpenAPI spec is generated by the backend; the Flutter client can be generated from it.
- **No PostgREST/Supabase-direct reads** from the client — everything goes through the FastAPI API.
- Remote access for draft night: Tailscale (later Cloudflare Tunnel + Access). Draft-night fallback UI is a
  backend-served HTML page — if the Flutter app isn't usable by draft night (Fri 2026-09-04), that's the plan.
- Jira project **`LS`** (shared with the backend). Commit subjects `LS-N: ...`.

## Working conventions
